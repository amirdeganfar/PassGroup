A rescue we priced last year

A café chain came to us with a loyalty app that crashed every time more than a few hundred members logged in. The code itself was workable — the problem was everything the first build had skipped: no load testing, no documentation, passwords pinned into the app's settings. The three states a badly built app lands in

Cosmetically broken. The app works but looks and feels poor — confusing screens, slow pages, clunky flows. The foundation is fine; the surface isn't.

Functionally broken. Features fail: payments drop out, logins loop, data saves twice or not at all. This is code-level trouble, and patches on top of patches get expensive fast.

Foundationally broken. The app can't grow — add users and it buckles, add features and old ones break. Most rebuilds trace back to this state, and the tell is that every new "quick fix" takes longer than the last.

The state matters because it decides the bill. Cosmetic work is design money. Functional work is developer time, and the price grows with how tangled the code is. Foundation trouble is the expensive one: no amount of patching turns a shaky foundation into a solid one.

The cost to fix a bad app: rescue vs rebuild

Every rescue quote starts with an audit — a developer reading the code and infrastructure to answer "worth saving?" The figures below are typical Australian budget bands for small-to-mid apps; every project swings on what the audit finds. The fork between repairing and rebuilding is the whole decision, and our number line puts rough bands on it:

Audita few thousand, one to two weeks — always first
Patch jobsroughly $1.5k–$8k for isolated bugs and UI fixes
Rescueroughly $10k–$30k for structural repairs, security, testing
Rebuildroughly $20k–$100k+ — effectively a second build

Treat those as budget planning bands, not quotes. A stable app with ugly screens might genuinely cost $5k to transform; an abandoned project with no documentation rarely stops at $20k. And note what the bands share: the cheaper paths all start with the same audit. Skipping it to "save money" is how founders end up paying for repairs twice.

Three real outcomes we've priced, to make the fork concrete. A retail founder with clean code and lost passwords: one-week fix, low thousands. A booking app with tangles in the payment code: three-month rescue, mid band. An abandoned build with no source code: rebuild, top band, and the only good news was that the founder owned the store account and kept her users. Same mistake at different depths — the audit is what tells you which one you're in.

What an audit costs before any fixing starts

Budget for it even when money is tight — the audit is the cheapest decision you'll make in the whole rescue. It should end with a written answer: what's salvageable, what's risky, and a fix-vs-rebuild recommendation with prices. A proper rescue then runs in this order:

  1. Audit

    Code review, security check, infrastructure look. No fixing yet — just a map of what's wrong and what's worth keeping.

  2. Stabilise

    Stop the bleeding: the crashes and data problems that cost you users every day get fixed first.

  3. Decide

    With real numbers: continue rescuing section by section, or cut losses and rebuild what's rotten.

  4. Rebuild forward

    Whether rescued or rebuilt, ship in small safe steps — never another big-bang rewrite with no feedback.

Watch the ongoing costs too. A rescued app still needs care — patching, platform updates, monitoring — and our guide to app maintenance cost per year shows the budget to expect once it's healthy.

Why missing source code doubles the bill

Source code is the human-written instructions your app is built from — the thing a developer needs to change anything. If you don't have it, in a repository you control, every fix starts with reverse-engineering your own product. That alone can double the repair bill, and if the original developer is gone entirely, you're straight into rebuild territory — see what happens when an app developer disappears. Ownership is also a consumer right worth knowing: under Australia's consumer guarantees, services must be provided with due care and skill, and that gives you grounds to seek a remedy when they aren't. Our page on who owns the app code explains how to make sure you're the owner from day one.

The cheapest rescue is the one you never need: own the code, read the quote properly, and pay against working software.

Prevention for your first build

Three habits prevent most bad-app stories. Put IP ownership in the contract — the code is yours, in writing, before work starts. Pay against milestones that deliver working software, never a big upfront sum. And insist on a testing and handover step: a written list of what was built, how it works, and where everything lives. Any good developer expects all three; a bad one argues.
